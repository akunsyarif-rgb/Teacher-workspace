1. RINGKASAN EKSEKUTIF
--------------------------------------------------------------------------------
Aplikasi: dua aplikasi dalam satu proyek Next.js 16 / React 19:
  (a) Teacher Workspace ("/")  — jurnal, presensi, nilai, tugas, pengumuman,
      analitik, wali kelas, jadwal, kas kelas, inventaris, backup, akun/paket.
  (b) Student Companion ("/student") — jadwal, tugas & pengumpulan, nilai,
      kehadiran, pengumuman, profil, ulangan (modul opsional).
Backend: Firebase Auth + Firestore (utama), Supabase (lampiran tugas privat dan
modul Ulangan Harian), Midtrans Snap (pembayaran), Firebase Admin SDK di route
server. Hosting yang dituju: Vercel.

Penilaian jujur:
- Fondasi keamanan dan keandalan sudah jauh lebih kuat dibanding awal siklus
  audit (lihat bagian 4 dan 5). Seluruh suite tes otomatis hijau dan CI GitHub
  pada main berstatus sukses.
- LAYAK untuk pilot terbatas / sekolah kecil-menengah dengan pemantauan.
- BELUM layak untuk penjualan skala besar tanpa menyelesaikan butir P0 di
  bagian 12: (1) pembaruan dependensi dengan kerentanan kritis/tinggi
  (khususnya Next.js 16.3.0), (2) urutan rilis aturan Firestore vs aplikasi
  yang sudah menimbulkan satu insiden nyata, (3) langkah manual pemilik yang
  masih tertunda (migrasi Supabase, TTL, uji Midtrans sandbox, Sentry),
  (4) tinjauan hukum atas dokumen Privasi/Syarat yang masih draf.
- Biaya Firestore (model uji beban sekolah 1.296 siswa/60 guru): perkiraan
  Rp 183 ribu/bulan, sekitar 15% dari pendapatan paket sekolah yang diasumsikan
  — sehat, dengan syarat asumsi pemakaian terbukti saat pilot.

Insiden terbaru yang relevan (12 Nov 2026): guru melaporkan "Missing or
insufficient permissions." saat mengubah presensi. Penyebab paling mungkin
(terbukti di emulator): aturan Firestore baru (wajib createdBy) ter-deploy
otomatis saat merge, sedangkan aplikasi di perangkat masih versi lama. Lihat
bagian 8.

3. ARSITEKTUR [TERVERIFIKASI, mengacu AGENTS.md]
--------------------------------------------------------------------------------
- Alur berlapis: Presentasi -> Controller -> Service -> Repository -> Adapter ->
  Firestore. UI tidak menyentuh Firestore langsung; Repository satu-satunya
  lapisan yang menyentuh Adapter.
- Multi-tenancy: semua koleksi wajib bidang workspaceId; semua query
  repository difilter workspaceId; WorkspaceContext hanya state sesi.
- Immutable: workspaceId, createdBy, createdAt tidak boleh diubah (ditegakkan di
  firestore.rules lewat keepsTenantImmutables()).
- Timestamp: createdAt/updatedAt dari serverTimestamp().
- Cache berlapis (baru siklus ini):
    * sessionCache (memori, TTL 15-60 dtk) dibuang saat guru menyimpan.
    * persistentCache (localStorage perangkat): cache turunan (daftar kelas,
      jadwal, angka hari lampau; TTL 10-30 menit; dibuang oleh clearAllCached)
      dan "syncStore" (sinkron bertahap presensi siswa & Analitik; draf
      formulir). Semuanya dibuang saat keluar akun.
- Skema data utama (koleksi Firestore): workspaces, teacher_profiles,
  workspace_invites, students, student_profiles, student_login_codes,
  schedules, journals, attendances, grade_columns, grades, assignments,
  submissions, announcements, student_notes, student_achievements,
  class_fund_transactions, class_inventory, session_skip_reasons,
  academic_years, payments; plus koleksi internal server (rate_limits,
  class_rename_jobs). Supabase: lampiran tugas (bucket privat) dan modul
  Ulangan.

4. KEAMANAN
--------------------------------------------------------------------------------
4.1 Yang sudah dikerjakan [TERVERIFIKASI lewat kode + tes aturan emulator]
- Aturan Firestore: isolasi tenant; field tenant immutable; batas kelas dan
  kedaluwarsa paket ditegakkan server (/api/students/create), bukan hanya UI;
  hapus berbasis peran (pembuat dokumen atau OWNER/ADMIN); hapus permanen
  hanya OWNER/ADMIN; siswa hanya membaca data kelasnya; catatan konseling
  (student_notes) tidak pernah terbuka untuk siswa; create wajib createdBy =
  uid pengguna (tidak bisa memalsukan pembuat).
- Webhook Midtrans: transaksional, verifikasi nominal, signature konstan-waktu,
  balasan non-2xx saat gagal agar Midtrans mencoba ulang.
- Kode akses siswa / kode undangan guru: CSPRNG, diverifikasi di server, ada
  rate limit; bergabung sebagai TEACHER hanya lewat /api/workspace/join (cek
  kode, kedaluwarsa, kuota kursi atomik).
- Autentikasi server: requireAuth terpusat dengan pengecekan pencabutan sesi
  (checkRevoked) — dikecualikan eksplisit hanya untuk autosave Ulangan.
- Error API disanitasi (tidak membocorkan pesan mentah SDK); skema Zod di
  batas API.
- Unggahan: validasi tipe/ukuran ketat, rate limit untuk penandatanganan URL
  dan ekspor backup, maksimum 10 lampiran per pengumpulan, bucket privat dengan
  signed URL 5 menit.
- Header keamanan: CSP (tanpa unsafe-eval di produksi), HSTS, dsb.
- Draf/cached data di perangkat dibuang saat keluar akun, dengan peringatan bila
  masih ada isian belum tersimpan.

4.2 Temuan terbuka
[P0] Dependensi rentan (npm audit --omit=dev, 12 Nov 2026):
     24 kerentanan: 2 kritis, 11 tinggi, 10 sedang, 1 rendah.
     - next 16.3.0 (kritis; rentang rentan 16.0.0–16.4.0; versi stabil
       terbaru 16.4.6). Isu yang tercantum: RCE tanpa autentikasi pada server
       berbasis Windows, RCE pada Image Optimization API (AVIF), RCE pada
       next/og ImageResponse, kebocoran Draft Mode pada "use cache".
       Penerapan pada app ini: kode TIDAK memakai next/image, next/og, maupun
       "use cache" (dicari di app/src/lib) dan hosting Vercel bukan Windows,
       sehingga paparan nyata kemungkinan rendah — tetapi tetap WAJIB
       dinaikkan ke 16.4.6 (pembaruan minor, risiko regresi kecil).
     - dompurify <=3.4.16 (kritis, transitif — dibawa jspdf): isu XSS pada
       mode IN_PLACE/hook. App tidak memakai dompurify langsung (tidak
       ditemukan di kode); naikkan jspdf agar ikut membawa versi perbaikan.
     - Tinggi (transitif): axios, follow-redirects, sharp, @grpc/grpc-js
       (lewat firebase/firebase-admin), @fastify/busboy, brace-expansion,
       re2js, source-map-js. Sebagian besar hanya terjangkau di sisi server
       atau saat build. `npm audit fix` tanpa --force menyelesaikan sebagian;
       saran npm untuk firebase ("turun ke 9.14.0") TIDAK boleh diikuti
       (downgrade mayor); cari versi firebase/firebase-admin terbaru yang
       membawa grpc-js perbaikan.
     Langkah: naikkan next, jspdf, firebase-admin/firebase; jalankan ulang
     seluruh tes + e2e; pasang Dependabot/Renovate dan job `npm audit` di CI.
[P1] CSP masih memakai 'unsafe-inline' untuk script/style (keterbatasan Next.js
     App Router tanpa nonce). Mitigasi: CSP berbasis nonce (utang teknis
     tercatat).
[P1] Data lama tanpa createdBy: baru dicap sejak 8 Nov 2026. Konsekuensi:
     (a) hanya OWNER/ADMIN yang bisa menghapus dokumen lama; (b) pemisahan
     per-guru di Beranda/Analitik memperlakukan jadwal lama sebagai milik
     semua guru sampai dibuat ulang. Tidak ada skrip migrasi/backfill.
[P1] Ulangan Harian: dimatikan default (NEXT_PUBLIC_ULANGAN_ENABLED). Bila
     diaktifkan butuh migrasi Supabase + identitas guru/siswa di Supabase.
     Tes DB Ulangan di lingkungan audit ini dilewati (butuh Postgres) — CI
     menjalankannya lewat workflow tersendiri.
[P2] Rate limiter bergantung pada koleksi rate_limits; TTL pada
     rate_limits.expiresAt BELUM dipasang (tugas pemilik) -> dokumen menumpuk.
[P2] Tidak ada Audit Log penghapusan/penghapusan permanen (hanya log server
     "trash.purged").
[P3] Skenario "guru dikeluarkan dari workspace saat sesi masih aktif" tidak saya
     uji secara khusus pada audit ini; disarankan ditambahkan sebagai tes.

--------------------------------------------------------------------------------
Data uji: 97.128 dokumen (36 kelas x 36 siswa, 60 guru, 180 hari sekolah).
Angka bacaan eksak; waktu ms berasal dari emulator (bukan latensi produksi).

- Beranda guru, buka berikutnya                    ±3.483         28
- Daftar kelas, buka berikutnya                     1.296          0
- Analitik guru, buka pertama (±3 kelas)           ±10.700      2.700
- Analitik OWNER/ADMIN (seluruh workspace)         ±10.700      7.920
- Kehadiran siswa, buka berikutnya                    720         24
- Riwayat presensi/jurnal satu kelas                  720        720
- Jadwal guru                                         720        720

Estimasi bulanan sekolah besar (60 guru, 1.296 siswa, 60% siswa aktif, 22 hari
sekolah): ≈ 18,9 juta bacaan -> ≈ US$ 11,4 ≈ Rp 183 ribu/bulan (Firestore saja).
Dibanding pendapatan paket sekolah yang diasumsikan (Rp 240 ribu/kursi/tahun x
60 guru ≈ Rp 1,2 juta/bulan): ≈ 15%.
Catatan kejujuran:
- Profil pemakaian dan "guru mengajar ±3 kelas" adalah ASUMSI. Guru nyata
  biasanya mengajar 5-8 kelas, sehingga hemat nyata Beranda/Analitik lebih
  kecil dari angka di atas. Ukur saat pilot.
- Sebagian penurunan biaya siswa berasal dari KOREKSI skenario uji (versi lama
  melebih-lebihkan dengan membuka semua halaman sekaligus).
- Biaya Vercel, Supabase, Auth, Storage, Midtrans tidak dimodelkan.
Sisa kekhawatiran performa:
[P2] Buka pertama di perangkat baru masih memuat semua jadwal + daftar kelas
     (±2.000 bacaan).
[P2] Riwayat presensi/jurnal per kelas memuat setahun penuh (perlu paginasi
     "muat lebih lama").
[P2] Staleness yang disengaja: daftar kelas/jadwal ≤10 menit, Analitik ≤30
     menit, rekap presensi/jurnal hari lampau (>3 hari) hingga sinkron penuh
     7 hari; presensi siswa (>7 hari) hingga 14 hari. Perubahan dari

8. INSIDEN TERBARU: "Missing or insufficient permissions." (Presensi, 12 Nov)
--------------------------------------------------------------------------------
Gejala: banner merah saat guru mengubah presensi di iPad (07.51 WITA, ±6 menit
setelah PR #82 di-merge).
Bukti (emulator + aturan nyata, tes baru tests/attendance-autosave-rules.test.ts):
- Klien versi baru: buat -> ubah -> tandai selesai LOLOS; juga untuk dokumen
  lama tanpa createdBy dan dokumen buatan guru lain.
- Klien versi LAMA (tidak mengirim createdBy saat membuat) DITOLAK dengan pesan
  yang persis sama.
Akar masalah proses: workflow deploy-firestore-rules.yml men-deploy
firestore.rules ke Firebase SEGERA saat main berubah, sedangkan bundel aplikasi
baru di Vercel baru siap beberapa menit kemudian dan perangkat dapat
menyimpan bundel lama lebih lama lagi (PWA/Safari). Jendela ketidakcocokan ini
akan berulang setiap rilis yang mengetatkan aturan.
Yang sudah dilakukan: pesan gagal-simpan kini jelas ("Muat ulang halaman ...")
di Presensi/Jurnal/Nilai; addDocument gagal dini bila tak ada sesi login; tes
aturan auto-save ditambahkan.
Rekomendasi [P0/P1]:
 1. Pola expand/contract: rilis pertama MELONGGARKAN aturan agar menerima klien
    lama & baru; rilis berikutnya (setelah semua klien ter-update) mengetatkan.
 2. Atau tahan deploy aturan sampai deployment Vercel berstatus READY
    (workflow_run / deployment_status).
 3. Tambahkan pengecekan versi klien (mis. endpoint /api/version + banner
    "Ada pembaruan, muat ulang") agar perangkat lama dipaksa memuat ulang.
 4. Tes kompatibilitas klien-lama pada setiap perubahan firestore.rules.
Tindak lanjut pemilik: pastikan deployment Vercel terbaru dari main berstatus
Ready; tutup dan buka ulang aplikasi di iPad (atau hapus data situs Safari).
